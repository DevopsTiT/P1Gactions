PII prevent step-by-step (your first-wave keys)

REAL EXAMPLE
Bad: log JSON with policyHolderName, subscriberDOB, bankAccountNo, telephoneNumber, EmailAddress1
Good: log only policyId, result, durationMs

STEP 1 APP
- Load pii-keys-blocklist.txt
- Scrub/remove those keys before logger.info
- PRD: never log full request/response bodies for policy/payment APIs

STEP 2 ONEAGENT
Settings → Sensitive data masking (OneAgent logs)
- Enable built-in email
- Custom regex: "policyHolderName":"..." → "***" (same for subscriberDOB, bankAccountNo, telephoneNumber, …)
- Scope to C_ALJ_BU_… PRD host/process groups
- Test with FAKE data only

STEP 3 OPENPIPELINE
Settings → OpenPipeline → Logs → Processing
- Match dt.host_group.id in your four C_ALJ_BU_… groups
- fieldsRemove high-risk attributes
- DQL replacePattern on content for "key":"value"
- Sample-test bad JSON → save

STEP 4 VERIFY
- Emit fake PII test log
- Run pii-scan.dql → no cleartext values

STEP 5 RUNBOOK R1–R6
R1 new Name/Kana/Address/Tel/DOB/mail/bank → blocklist/approval
R2 no PRD full-body API logs
R3 OpenPipeline required for new PRD log ingest
R4 weekly DQL scan
R5 masked demos only
R6 Grail PII = privacy incident

Rollout: Day1 top20 keys+OneAgent → Day2 OpenPipeline → Day3 full first-wave → weekly scan
