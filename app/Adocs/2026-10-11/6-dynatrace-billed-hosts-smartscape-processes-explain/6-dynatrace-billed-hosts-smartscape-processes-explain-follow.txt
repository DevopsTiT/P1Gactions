# Billed Hosts, Smartscape And Processes Query

## Decision tree

```
Cell result?
 Billed hosts line, asked 15m but shows 30 min   → cell N: too many buckets for a month → Dynatrace widened them
     dips in the line                           → hosts off, agent gaps, or late billing records
 Red error "summarize ... missing: aggregation"  → cell O: summarize needs count() or similar → add nodes = count()
 Very long query with fixed timestamps           → cell P: generated by the Infrastructure & Operations app
     what it builds                             → the Processes table: process, health, alerts, tech, host, group
     filter name == "ctm-ag-uploader.jar"       → you were checking the Control-M agent uploader process
     need something simpler?                    → P1 list, P2 open events, P3 availability and CPU
```

## Short takeaway

| Cell | What it does | Result | Main point |
|---|---|---|---|
| N | Billed Infrastructure Monitoring hosts over time | 1 series, February | Asked for 15-minute buckets, got 30, because a month of 15-minute buckets is too many. |
| O | Count AWS nodes per AWS account | Error | `summarize` needs an aggregation such as `count()`. |
| P | Processes table with health, alerts, technology, host and group | Long generated query | Built by the Infrastructure & Operations app, filtered to `ctm-ag-uploader.jar`. |

## Summary

Cell N is the last billing cell and works. Cell O fails on a small syntax rule. Cell P is not hand-written: the Infrastructure & Operations app produces it when you open its Processes view in a notebook. It is long because it pulls health events, problems, technologies, hosts and groups for every process. For a single process like the Control-M uploader, three short queries give the same answers.

## Investigation

### Words you need first

| Term | What it means | Why you care |
|---|---|---|
| Bucket (interval) | The time slice each point covers. | Too many small buckets get widened automatically. |
| `countDistinct()` | Counts different values. | Number of different hosts per bucket. |
| `smartscapeNodes` | Newer command that reads the Smartscape topology (the map of hosts, services and cloud resources) stored in Grail. | Used in cell O. |
| Aggregation | A function that turns many rows into one number: `count()`, `sum()`, `avg()`, `max()`. | `summarize` needs at least one. |
| Davis event | Something Davis (the Dynatrace AI engine) detected on an entity, such as high GC or process unavailable. | Feeds the health columns in cell P. |
| Davis problem | A group of related events that Davis treats as one incident. | Cell P links events to problems. |
| `executionOrder:leftFirst` | Run the main query first, then the lookup only for the rows that are left. | Makes long lookups faster. |
| `union:true` | In `timeseries`, keep a row if any of the listed metrics has data. | Some processes report only one metric. |

### Cell N: number of billed hosts

```
fetch dt.system.events
| filter event.kind == "BILLING_USAGE_EVENT" and event.type == "Infrastructure Monitoring"
| dedup event.id
| filter isNotNull(billed_host_hours)
| filter billed_host_hours > 0
| makeTimeseries host_count = countDistinct(dt.entity.host), interval: 15m, time: usage.start
```

| Line | What it does |
|---|---|
| `filter event.kind ... event.type ...` | Only Infrastructure Monitoring billing records |
| `dedup event.id` | One copy per record |
| `isNotNull` and `> 0` | Skip empty or zero records, so a host is counted only when it was really billed |
| `makeTimeseries countDistinct(dt.entity.host), interval:15m` | How many different hosts were billed in each time slice |

| Result | Meaning |
|---|---|
| Timeframe 2/1 10:52 to 2/28 10:52 | 27 days |
| Interval shows 30.00 min, not 15 | 27 days of 15-minute buckets is about 2,600 points. That is over the limit, so Dynatrace doubled the bucket size. |
| Flat line with small dips | The host count is steady. Dips are short moments with fewer billed hosts: restarts, agent gaps, hosts switched off, or billing records that arrive late. |

Use `interval:1h` for a month, or `15m` for a day or two.

### Cell O: smartscapeNodes error

```
smartscapeNodes "AWS*"
| summarize by:{aws.account.id}
```

| Point | Explanation |
|---|---|
| What it wants | All Smartscape nodes whose type starts with `AWS`, grouped by AWS account |
| Error | "There aren't enough parameters for command 'summarize'. 1 mandatory parameter is missing: aggregation" |
| Why | `summarize` must calculate something. `by:` alone only says how to group. |
| Fix | `summarize nodes = count(), by:{ aws.account.id }` |

### Cell P: the Processes query from Infrastructure & Operations

This query is generated. The fixed timestamps (`2026-04-01T05:59:13.649Z` to `07:59:13.649Z`, which is 14:59 to 16:59 JST) are the app's timeframe at the moment it was opened in a notebook.

#### Part 1: the processes

```
fetch dt.entity.process_group_instance
| fieldsAdd name = entity.name, ebpfHasPublicTraffic, tags = coalesce(tags, array())
| fieldsAdd cesPlaceholder = "classicEntitySelector placeholder"
| filter name == "ctm-ag-uploader.jar"
/// filter name == "p_ctmat"
```

| Line | What it does |
|---|---|
| `fetch dt.entity.process_group_instance` | Every monitored process |
| `ebpfHasPublicTraffic` | Whether the process talks to the internet, as seen by the eBPF network sensor |
| `coalesce(tags, array())` | Use an empty list when a process has no tags, so later steps do not break |
| `cesPlaceholder` | A spot where the app inserts its own entity selector filter. Here it does nothing. |
| `filter name == "ctm-ag-uploader.jar"` | Only the Control-M agent uploader process |
| `/// filter name == "p_ctmat"` | Commented out. `p_ctmat` is another Control-M agent process. |

#### Part 2: health events per process (the first big lookup)

| Step | What it does | Why |
|---|---|---|
| `fetch dt.davis.events.snapshots` from start minus 370 minutes to end plus 1 minute | Davis events, looking back about 6 hours before the window | Catches events that started earlier and are still open |
| Keep events on processes, not INFO | Only real findings on process instances | Skip noise |
| `dedup event.id, sort:{timestamp desc}` | Keep the newest snapshot of each event | An event has many snapshots as it changes |
| `filterOut event.provider == "ROOT_CAUSE_ANALYSIS"` | Drop events created by root cause analysis | Avoid counting the same thing twice |
| Keep events that overlap the window | Open events, or ones that ended inside it | Only what matters for this window |
| Inner `lookup` on `dt.davis.problems` | For each event, find the problem it belongs to | Mark events under investigation |
| `filter true == false OR event.status == "ACTIVE" OR investigationMode > 0` | `true == false` is a switch the app turned off. It keeps active events and events linked to problems. | A template trick |
| `expand affected_entity_ids` | One row per affected process | Match back to processes |
| `isHealthAlert` | Marks built-in health types: high GC activity, process unavailable, network loss rate, connection failure rate | Health column vs custom alerts column |
| `summarize ... by affected_entity_ids` | Per process: health indicators, custom alerts, and counts of active, closed and warning events | One row per process |
| `eventsThreshold` | 2 = active problem, 1 = active warning, 0 = only closed events, -1 = nothing | Color of the health dot in the app |

Then it sorts processes with health issues first and keeps 1,000.

#### Part 3: extra columns (more lookups)

| Lookup | What it adds | How |
|---|---|---|
| Technologies | `softwareTechnologies`, such as JAVA or NODE_JS | Parses the `type:` part of each technology record |
| Host | `hostRecord` with host ID and host name | A `timeseries` over three metrics, grouped by host and process |
| Process group | `groupName` | The same trick, grouped by process group |
| Further lookups (cut off) | Most likely CPU, memory and availability values | Same pattern |

Why the `timeseries` trick: the app needs to know which host and group each process belonged to inside the window. It asks for three metrics with `union:true`, because different processes report different metrics:

| Metric | Reported for |
|---|---|
| `dt.process.cpu.usage` | Every process, including short-lived ones |
| `dt.process.availability` | Processes on hosts in discovery mode |
| `dt.host.zos.gcp_time` | z/OS mainframe processes |

## Result

| Cell | Verdict | Fix or use |
|---|---|---|
| N | Works | `interval:1h` for a month |
| O | Syntax error | `summarize nodes = count(), by:{ aws.account.id }` |
| P | Works, very long | Leave it to the app. Use P1, P2 and P3 for one process. |

What the cell P filter tells you: you were checking whether `ctm-ag-uploader.jar` (the Control-M agent part that uploads job output) is running and healthy on its hosts. That links to the Control-M alerts we migrated.

Common mistakes:

| Mistake | How to avoid it |
|---|---|
| Small intervals over long ranges | Match the interval to the range: 15m for a day, 1h for a month |
| `summarize by:` with no aggregation | Always add at least `count()` |
| Editing a generated app query by hand | Copy only the parts you need into a short query |
| Fixed timestamps in a copied query | Replace them with `from:now()-2h` before reuse |

## Data flow map

```
Billing
  dt.system.events (BILLING_USAGE_EVENT, Infrastructure Monitoring) → countDistinct hosts per bucket → cell N

Topology
  smartscapeNodes "AWS*" → summarize count() by aws.account.id → cell O

Processes table (Infrastructure & Operations app)
  dt.entity.process_group_instance (filter ctm-ag-uploader.jar)
    ├─ lookup dt.davis.events.snapshots ── lookup dt.davis.problems → health, alerts, eventsThreshold
    ├─ lookup softwareTechnologies → technology
    ├─ lookup timeseries (cpu, availability, zos) by host → hostRecord
    ├─ lookup timeseries by process group → groupName
    └─ more lookups (cut off) → metrics
  → sort by health → limit 1000 → Processes table
```
