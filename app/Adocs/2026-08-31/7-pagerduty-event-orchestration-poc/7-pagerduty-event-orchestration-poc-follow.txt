================================================================================
WHAT THIS IS (vs four AI agents)
================================================================================

This notepad = Event Intelligence / Event Orchestration / Alert Grouping.
Four agents (SRE/Scribe/Shift/Insights) = AFTER a clean incident exists.
Do this POC first if your pain is alert storms and wrong-team pages.

Architecture:
Dynatrace Problem / Events API
  -> Event Orchestration (route / pause / suppress / annotate)
  -> Target Service (db / infra / app / default)
  -> Alert Grouping (intelligent / by host)
  -> One Incident -> test EP (only you)
  -> optional later: AI agents

================================================================================
DECISION TREE
================================================================================

Many related alerts -> one page?
  Same app repeats          -> #1 Intelligent grouping
  Many processes one host   -> #2 Group by host
  disk+cpu+memory one host  -> #3 Content group by host
  Disk repeats one host     -> #4 Group by host (+ disk class optional)

Right team?
  Oracle/DB                 -> #5 Route poc-eo-db
  Linux/OS                  -> #6 Route poc-eo-infra
  Java/Tomcat/app           -> #7 Route poc-eo-app
  Unknown                   -> #10 Default poc-eo-default

Do not wake people?
  Self-resolves quickly     -> #8 Pause 3-5 min
  Caused by deploy          -> #9 Change Event + pause/suppress + resolve

Always: TEST Integration Keys only.

================================================================================
0) SHARED SETUP
================================================================================

Create Services:
- poc-eo-default
- poc-eo-db
- poc-eo-infra
- poc-eo-app

All on escalation poc-eo-ep (notify ONLY you).
Each Service: Events API v2 (or Dynatrace) test Integration Key.
poc-eo-infra + poc-eo-app: enable Alert Grouping (Intelligent and/or content by host).
AIOps -> Event Orchestration -> poc-eo-orchestration (Global or ingress).

Orchestration rule order (top to bottom):
1. Pause/suppress deploy + flapping (#8 #9) — narrow matches
2. Route Oracle/DB (#5)
3. Route Java/Tomcat/app (#7)
4. Route Linux/OS (#6)
5. Default -> poc-eo-default (#10)

================================================================================
1) INTELLIGENT GROUPING — SAME APP REPEATS
================================================================================

Goal: repeated Checkout latency alerts -> ONE incident.

1) poc-eo-app -> Settings -> Alert Grouping -> Intelligent ON
2) Send 3-5 triggers same app / similar summary within a few minutes
3) Confirm one incident; Alerts tab shows multiples
4) Resolve

Pass: one incident, not one page per alert.

================================================================================
2) 20 PROCESSES DOWN SAME HOST -> 1 INCIDENT
================================================================================

Goal: many process-unavailable on host=app-01 -> one incident.

1) Content-based grouping keyed by host on poc-eo-infra (or app)
2) Send 5-10 (or 20) triggers same host=app-01, process unavailable summaries
3) Confirm one incident
4) Optional: host=app-02 should be a separate incident

Pass: same host merges; different host does not.

================================================================================
3) DISK + CPU + MEMORY SAME HOST -> 1 INCIDENT
================================================================================

Goal: different metric titles on one host still group.

1) Grouping key = host (not summary)
2) Send three triggers host=app-01: Disk / CPU / Memory
3) Confirm one incident with three alerts
4) Disk on host=app-02 -> second incident

Pass: cross-metric group on one host.

================================================================================
4) DISK SPACE SAME HOST -> 1 INCIDENT
================================================================================

Goal: rising disk % alerts on db-01 do not storm.

1) Keep host grouping on poc-eo-infra
2) Send three disk triggers host=db-01 (90/92/95)
3) Confirm one incident shows progression
4) Resolve

Pass: disk storm collapsed.

================================================================================
5) ORACLE -> DB TEAM
================================================================================

EO rule: IF summary/details match Oracle|ORA-|tablespace|listener
THEN route poc-eo-db

1) Add route rule
2) Send: Oracle tablespace USERS 95% full
3) Incident on poc-eo-db only
4) Non-DB event must NOT land on db

Pass: correct Service + negative path.

================================================================================
6) LINUX/OS -> INFRA TEAM
================================================================================

EO rule: IF Linux|systemd|kernel|OS|host unavailable -> poc-eo-infra
Place after DB if overlap possible.

1) Add route
2) Send: Linux systemd unit httpd.service failed on app-01
3) Incident on poc-eo-infra
4) Optional: combine with #2/#3 grouping

Pass: infra owns OS.

================================================================================
7) JAVA/TOMCAT -> APP TEAM
================================================================================

EO rule: IF Tomcat|JVM|GC pause|java OR application field set -> poc-eo-app
Optional annotate application=<name>

1) Add route
2) Send: Tomcat thread pool exhausted + custom_details.application=checkout
3) Incident on poc-eo-app
4) Optional: Intelligent grouping (#1) on same Service

Pass: app owns runtime.

================================================================================
8) SELF-RESOLVE -> AUTO PAUSE / NO ALERT
================================================================================

EO Pause 5 minutes for flapping signature (wait time|GC pause|transient — tune).

Happy: trigger then resolve within 2 min -> no page
Negative: trigger, no resolve -> after pause, incident appears

Safety: narrow match; document delay so stakeholders know.

Pass: self-heal silent; real outage still pages.

================================================================================
9) DEPLOYMENT -> CHANGE CONTEXT + SELF CLOSE
================================================================================

Path A (recommended): Change Event on Service + Pause/suppress known deploy blip
Path B: incident opens with change on timeline; Dynatrace resolve auto-closes PD

1) Add Change Event: Deploy checkout 1.2.3 on poc-eo-app
2) EO: known deploy noise -> Pause 10m (or windowed suppress)
3) Send CPU spike on checkout during window
4) Path A: no lasting page; change visible
5) Path B: if open, send resolve -> auto-resolve
6) Do NOT suppress customer-impact titles in the same rule

Pass: change visible; deploy blip does not leave false page.

================================================================================
10) UNKNOWN -> DEFAULT TEAM
================================================================================

Last rule: ELSE route poc-eo-default

1) Catch-all at BOTTOM
2) Send: Something completely new xyz-unknown-42
3) Lands on poc-eo-default
4) Re-send Oracle event -> still poc-eo-db (order proof)

Pass: unknown owned; specific rules still win.

================================================================================
HALF-DAY ORDER
================================================================================

0) Setup 45-60m
1-4) Grouping 30-40m
5-7 + 10) Routing 30-40m
8-9) Pause + deploy 30-40m

================================================================================
COMMON MISTAKES
================================================================================

Catch-all first          -> move to bottom
Grouping off             -> enable on destination Service
Group by summary only    -> use host for #2-4
Pause too broad          -> narrow; prove negative path
Suppress all on deploy   -> only known blips
Prod Integration Keys    -> use test keys only
Expect AI agents to fix storms -> EO first, agents later
