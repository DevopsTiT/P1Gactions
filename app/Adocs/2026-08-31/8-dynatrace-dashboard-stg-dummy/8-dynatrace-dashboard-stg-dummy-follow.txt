Dynatrace dashboard — try STG first with dummy data
(OneAgent + synthetic traffic / demo app)

WHAT THIS IS
A Dynatrace dashboard is one screen of health tiles for L1.
STG = staging (not customer traffic).
Dummy data here = synthetic monitors + load script + intentional STG failures.
You still get real Dynatrace signals from STG OneAgents.

WHY STG FIRST
Prove all 11 sections light up safely before cloning to prod.

YOUR 11 SECTIONS → STG DUMMY PASS
1 Overall Health — green baseline, then break something, see unhealthy/critical
2 Active Problems — count, severity, duration (leave one problem >15 min once)
3 Host health — CPU / memory / disk (+ 3 or 7 day trend after history exists)
4 Process health — stop process or low instance count
5 Application health — availability, request/response time, error rate
6 Top services — errors/latency + backends called (need slow + error stubs)
7 Log errors — ERROR / exception lines from demo app
8 Database health — availability, connections, response time (STG DB or stub)
9 AWS health — STG AWS integration + env:stg tags
10 L1 action required — new critical, problem >15m, host not reporting, app/process unavailable
11 Architecture / data-center — STG topology / Smartscape view

ORDER
A) Dashboard name L1-Health-STG + management zone tag env:stg + OneAgent on STG
B) Demo app + HTTP synthetic + load/error script + backend stubs
C) Inject L1 scenarios in STG only (with approval for host/agent stop)
D) Checklist all pass → export/clone → retarget MZ to prod

RULES
- Do not build or break on prod first
- Do not mix prod entities on the STG board
- Empty Top services usually means no inter-service traffic yet
- Host 3/7 day trend is thin on day 1 — recheck later
- Mask PII even in STG logs
