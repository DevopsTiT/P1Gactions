The CloudWatch alert does not open a Dynatrace problem because its trigger never calls Dynatrace.

When the alarm becomes ALARM, CloudWatch does two things:
1. It runs the alarm actions. An email SNS topic sends mail. Dynatrace is not on that list.
2. It sends a state-change event to EventBridge. That event stays in AWS unless a rule has a Dynatrace API destination as the target.

Dynatrace's AWS connection polls metric numbers with GetMetricData, GetMetricStatistics, and ListMetrics. It does not read the alarm state. DescribeAlarms is not part of that poll. A custom log metric such as LambdaAppLogs / FailedToHandleCount is also outside the default metric list.

The preview that found CW test logs is a log search. It does not carry the alarm state, so Davis has no event to turn into a problem.

Check the alarm's Actions list, then EventBridge rules for source aws.cloudwatch and detail type CloudWatch Alarm State Change.
